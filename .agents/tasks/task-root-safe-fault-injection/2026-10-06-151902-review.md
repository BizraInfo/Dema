# Root-safe fault injection for the three permission-based test seams (v1)

Three test suites inject permission faults with `chmod` (0o000 / 0o500 / 0o400) and then assert the resulting read/write denial. The suite runs as `root` (uid=0), which bypasses DAC permission bits, so those `chmod` calls are no-ops and the fault under test never fires — producing 25 failures (22 in c4b2a-mechanical-rollback-wiring, 2 in authorship-key-store-negative, 1 CCB-19 in mission-corridor-closure-binding) while the production code is correct and CI (non-root ubuntu-latest) stays green. The change mirrors the repo's own canonical precedent (`tests/first-encounter-admission.test.js`): before each chmod-dependent assertion, a hermetic probe checks whether the specific denial actually fires for this process, and if it does not, the case calls `t.skip("filesystem does not enforce modes for this process")`. Real assertions are preserved so they still run on a mode-enforcing host. No production code and no G8 classifier were touched.

Watch for: the guards are genuinely conditional on real mode enforcement — the probe returns `false` only when the fault cannot fire, so a reverted production path would still fail on a mode-enforcing host (confirmed). The one cosmetic gap is a per-probe tmp directory the mission-corridor probe leaves behind (possible); permissions are always restored, so there is no cross-test state leak.

**Verdict**: APPROVED

## High-level view

The fix adds one probe function per file that reproduces the exact denial seam each suite relies on — `readFileSync` on a 0o000 file (authorship), `writeFileSync` into a `spawnSync chmod 0500` directory (c4b2a, the same seam its fixtures use), and `appendFile` to a 0o400 file (mission). The probe is the gate: it returns `true` only when the denial really fires, so on a mode-enforcing host every guarded case runs its real assertions unchanged, and on root it skips honestly instead of asserting a fault it could not create. This is a conditional guard, not a blanket mask — a broken production path would still fail where modes are enforced.

The 22 c4b2a skips include several schema-refusal cases (C4B2AS/C4B2AM) that do not chmod directly but reach their state through `atEffectApplied()` / `crossBoundaryDuringOutage()`, which require the 0o500 outage to fire; guarding them is correct, not over-broad, because their setup asserts `phase === "EFFECT_APPLIED"` and would fail if the outage silently succeeded.

The scope is held tight: only the three test files, the `CURRENT_LIMITS.md` note, and a task receipt changed. The classifier allowlist and all `packages/**` production code are untouched (verified by numstat — the only `packages/**` deltas are mode-bit-only). The `CURRENT_LIMITS.md` note is SHA-bound to HEAD and states plainly that a skip is not a pass: the adversarial invariants remain `VERIFIED` only on a mode-enforcing environment and `UNVERIFIED` on root.

### The probe is the gate, and it gates on the real denial

Each file adds a probe that reconstructs the exact primitive its assertions depend on. `authorship-key-store-negative` writes a file, `chmod`s it to 0o000, and tries `readFileSync` — returning `true` only if the read throws. `mission-corridor-closure-binding` writes a file, `chmod`s to 0o400, and tries `appendFile`. `c4b2a-mechanical-rollback-wiring` is the sharpest: it `mkdir`s a probe directory, runs `spawnSync("chmod", ["0500", guarded])` — the *same* seam `crossBoundaryDuringOutage`'s `trip()` uses — and tries `writeFileSync` inside it. Because the probe exercises the identical mechanism the fixtures use (external `chmod` via `spawnSync`, directory write-protection), it reflects precisely what that seam can and cannot enforce for the running process, rather than approximating it with a different syscall.

The behavioral property that matters: the probe returns `false` only when the fault genuinely cannot fire — verified directly on this host, where the c4b2a dir-write probe returns `false` under root. If the production rollback/recovery/refusal logic were reverted or broken, the guarded cases would still execute their preserved assertions and fail on a mode-enforcing host (CI, non-root). The skip hides an un-injectable fault, not a regression.

### The 22 c4b2a skips are not over-broad

A reviewer scanning the list will see cases like `C4B2AS-01: ROLLBACK_STARTED with empty evidence is refused` guarded by the write-denial probe, which looks unrelated to a write outage — the test is about schema/writer qualification, not an unwritable store. The dependency is transitive: these cases enter through `atEffectApplied()`, which calls `crossBoundaryDuringOutage(f, base, { blockOn: "undo" })` and then asserts `state.phase === "EFFECT_APPLIED"`. That durable `EFFECT_APPLIED` head only exists because the undo write was blocked by the outage; if the 0o500 chmod were a no-op, the undo would complete and the fixture's own precondition assertion would fail before the schema-refusal logic is ever reached. Guarding the whole case is therefore the correct granularity — there is no sub-assertion that is meaningful once the setup cannot be established.

### Hermeticity and permission restoration

All three probes restore permissions in a `finally`, so none leaves a locked file or directory that could poison a later test. Cleanup is asymmetric: the authorship probe registers its tmp dir in the shared `tempDirs` array cleaned by `after()`, the c4b2a probe `rmSync`s its own dir and caches its result once per process, but the mission probe restores the file mode and never removes its `mkdtemp` directory — a disk-cleanliness gap, not a state-isolation problem, since nothing locked survives.

### Scope and honesty of the claim

numstat on the working tree shows content changes in exactly four files plus the untracked receipt; `packages/**` shows only `100644->100755` mode-bit noise with zero content lines, and `scripts/ci/classify-known-harness-failures.mjs` has no diff at all — the no-false-GREEN classifier and its `KNOWN_MASKABLE` allowlist are untouched, so the suite goes green by honest skips rather than by name-masking a failure. The `CURRENT_LIMITS.md` note is bound to HEAD `01dbf8f`, enumerates the three suites and case counts, states the proof (harness honest on non-mode-enforcing hosts, full `npm test` G8-clean) and — critically — the non-proof ("a skip is not a pass … `UNVERIFIED` on `root`"). The receipt JSON records the same with a per-file skip breakdown.

Full-suite run observed in this review: `# tests 10126, # pass 10080, # fail 0, # skipped 46`, and `[G8 GATE] Clean run: 0 failures, 0 not-ok lines. Exit 0`. The three files run in isolation produced `# fail 0, # skipped 25` — the 25 skips are exactly the 25 previously-failing cases.

### Test coverage

The adversarial permission-denial behavior is covered on mode-enforcing hosts (CI) and honestly skipped on root. Not tested on root (by design, and disclosed): the actual read/write-denial recovery and refusal invariants behind the 25 guarded cases. There is no automated assertion that the probe and the fixture seam stay in agreement if a fixture later changes its injection mechanism (e.g. switches from `spawnSync chmod` to an in-process `chmod`) — a future divergence would silently change what the probe gates on. Low risk given both live in the same file, but worth a comment anchoring the two together.
